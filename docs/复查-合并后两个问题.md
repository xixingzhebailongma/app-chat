## 2. 问题 1：`spaces` 列表列错位

### 2.1 事实链（可逐行核对）

`wechat-gateway/src/db/src/PgSpaceRepository.cpp`

```cpp
// 32-43 行：列序注释写死 7 列
// 列序：space_id, name, type, enabled, source, active_scene_id, scenes_seeded。
Space parseRow(PGresult* res, int row) {
    ...
    s.active_scene_id = str(res, row, 5);    // 40
    s.scenes_seeded   = asBool(res, row, 6); // 41
```

```cpp
// 50-64 行
std::vector<Space> PgSpaceRepository::listAll() const {
    const std::string sql =
        "SELECT space_id, name, type, enabled, source FROM spaces ORDER BY name"; // 52 行：只有 5 列
```

同一个文件里 `listEnabled()`（68 行）和 `findById()`（86 行）都是 7 列，**只有 `listAll()` 漏了**。

Git 归属（`git blame`）：

- `7729dcb`（10-09）建了 5 列 SELECT；
- `c1e53b1`（10-10）给 `parseRow` 加了第 6/7 列，**只改了 `listEnabled` / `findById` 用到的路径，漏改 `listAll`**。
- 这两次提交都早于 wyr 的 `5d3b0ea`，**与本次前端同步无关**。

### 2.2 运行时到底会发生什么

`str()` 的实现是 `PQgetisnull(res, row, col) ? "" : PQgetvalue(...)`（24 行）。列号越界时，libpq 会把
`column number 5 is out of range 0..4` 写进**连接级 `conn->errorMessage` 缓冲区**，并把该列按 NULL 处理，于是：

- `active_scene_id` → `""`
- `scenes_seeded` → `false`

（该错误串确实来自 libpq：本机 `C:\msys64\ucrt64\bin\libpq.dll` 内含 `column number %d is out of range 0..%d`。是否真的「打印」取决于有没有人读 `PQerrorMessage()`——**本仓库 `grep PQerrorMessage` 结果为 0 处**，所以它只会烂在连接缓冲区里，下一次查询开始时被重置。）

因此上一版报告里的「日志刷屏（× 2 = 18 行）」**我无法证实**：仓库里没有任何代码会把这句话打到日志，`gw.err.log` 也是空的。若你确实在终端见过，那是别的运行方式（例如 psql/其他工具）产生的，不是网关。

### 2.3 影响面核实：为什么说「当前无用户可见症状」

`listAll()` 只有两个调用方：

| 调用方 | 用到的字段 | 是否受列错位影响 |
|---|---|---|
| `wechat-gateway/src/services/src/SpaceService.cpp:53`（`adminList`） | 只用 `space_id/name/type/enabled/source`，且 **JSON 只序列化这 5 个键**（54-58 行） | 否 |
| `wechat-gateway/src/services/src/SpaceSyncService.cpp:35`（边侧同步对账） | 只用 `space_id` / `source` / `enabled`（42-56 行） | 否 |

也就是说：

1. **`/api/admin/spaces` 从来就没返回过 `active_scene_id` / `scenes_seeded`**——不是因为 SELECT 少两列，而是 `adminList()` 就没往 JSON 里放。**只补 SELECT 这两列，接口响应不会有任何变化。**
2. `scenes_seeded` 是纯内部字段，只在 `SceneService.cpp:57-62` 的懒种判断里用，而那里走的是 `findById()`（7 列，正常）。**所以场景懒种没有被这次列错位影响。**
3. `active_scene_id` 的对外出口是 `GET /api/miniapp/scenes`（`SceneService.cpp:70`），同样走 `findById()`，正常。
4. 前端 `miniapp/src/pages/admin/space-detail.vue:254-258` 拿 `api.adminSpaces()` 只为找 `name/type/enabled` 做编辑表单，**没有读这两个字段**（全仓 `grep active_scene_id|scenes_seeded` 在 `space-detail.vue` 里 0 命中）。
5. `miniapp/src/api/mock.js:9-14` 的 mock 空间也只有 5 个字段，mock 与真实接口在这一点上**没有分叉**。

结论：这是**真实的代码缺陷（越界读 + 语义错误），但不是当前的故障源**。它的危险在于「静默」：哪天有人给 `adminList` 加上这两个字段，就会得到永远为空/永远 `false` 的假数据。

### 2.4 建议修复（两处，按需取舍）

**必改（1 行，消除越界读）：**

```diff
--- a/wechat-gateway/src/db/src/PgSpaceRepository.cpp
+++ b/wechat-gateway/src/db/src/PgSpaceRepository.cpp
@@
-        "SELECT space_id, name, type, enabled, source FROM spaces ORDER BY name";
+        "SELECT space_id, name, type, enabled, source, active_scene_id, scenes_seeded"
+        " FROM spaces ORDER BY name";
```

**可选（仅当管理端确实要展示「当前场景 / 是否已种场景」时才做）：**

```diff

@@
         arr.push_back({{"space_id", space.space_id},
                        {"name", space.name},
                        {"type", space.type},
                        {"enabled", space.enabled},
-                       {"source", space.source}});
+                       {"source", space.source},
+                       {"active_scene_id", space.active_scene_id},
+                       {"scenes_seeded", space.scenes_seeded}});
```

注意：第二处是**契约变更**（`openapi/miniapp.yaml:761-767` 对 `/api/admin/spaces` 只写了「含停用 + source」，没有字段清单）。加字段是向后兼容的，但要同步 `wechat-gateway/docs/前端miniapp-交接接口.md` 与 openapi，否则又会变成「文档与实现不一致」。

**建议同时加一道防复发护栏**：`parseRow` 里先断言 `PQnfields(res) >= 7`（或改成按 `PQfnumber` 取列号），这类「加列漏改某条 SELECT」的 bug 就能在第一次请求时炸出来，而不是静默返回空串。

## 3. 问题 2：`vite.config.js` 的 proxy 被删

### 3.1 事实链

`git show 5d3b0ea -- miniapp/vite.config.js` 明确删掉了 5 行：

```diff
   server: {
     host: true,
-    proxy: {
-      '/api':      { target: 'http://127.0.0.1:8080', changeOrigin: true },
-      '/internal': { target: 'http://127.0.0.1:8080', changeOrigin: true },
-      '/ws':       { target: 'http://127.0.0.1:8080', ws: true, changeOrigin: true },
-    },
   },
```

当前 `miniapp/vite.config.js` 只剩 `host: true`，事实成立。归属也成立：`5d3b0ea`（wyr，11-04 14:22，「miniapp: 同步最新前端实现」，改了 36 个前端文件）。

**但归因要改写**：该提交只有一个父提交，不是 merge。它把 `miniapp/` 整目录替换成新版，`vite.config.js` 自然按新版内容落盘，本地那 5 行就没了。正确说法是「**覆盖式提交夹带了本地配置的丢失**」，而不是「git 合并把功能切断了」。

### 3.2 为什么说它现在零影响（三条独立证据）

1. **前端所有请求都用绝对地址，压根不经过 Vite 代理。**

   `miniapp/src/config.js:15`
   ```js
   BASE_URL: env.VITE_BASE_URL || 'http://127.0.0.1:8080',
   ```
   `miniapp/src/api/index.js:5` `const base = () => config.BASE_URL`，之后每个调用都是 `base() + '/api/miniapp/...'`。
   WebSocket 同理：`miniapp/src/utils/ws.js:9-12` 由 `BASE_URL` 派生 `ws://127.0.0.1:8080`。
   全仓 `grep` 相对路径请求（`url: '/api...'`、`fetch('/api...')`、`XMLHttpRequest`）**0 命中**。

2. **本地 `.env` 明确写了绝对地址。**
   ```
   VITE_USE_MOCK=false
   VITE_BASE_URL=http://127.0.0.1:8080
   ```

3. **网关自己开了 CORS，跨域直连是通的。**
   `wechat-gateway/src/main.cpp:377-397`：OPTIONS 预检返回 204 并带 `Access-Control-Allow-Origin: *`、`Allow-Headers: Content-Type, Authorization`；所有响应再由 pre-sending advice 补 `Access-Control-Allow-Origin: *`。

补充：`proxy` 块在这个前端里是**历史遗留的死配置**——只有当 `BASE_URL` 为空、请求走相对路径时才会生效。文档也没依赖它：`miniapp/README.md:32-43` 教的是配 `VITE_BASE_URL`，全文没有提 proxy；`grep proxy` 只命中 `parent-h5`（那个项目 `OA_BASE_URL` 默认为空、确实靠 `parent-h5/vite.config.js:21-26` 的代理，**它的代理还在，没被动过**）。

### 3.3 那「404」是怎么来的？

按现有代码，浏览器打开 `http://localhost:5173/` 后请求会直接发往 `http://127.0.0.1:8080/api/...`，**不可能 404 在 5173 上**；网关没起时是 `ERR_CONNECTION_REFUSED`，网关起了但路由不对才是 404。三种可能的真相，按概率排：

1. 验证方式是 `curl http://localhost:5173/api/...`（直接打 Vite 端口）——删了 proxy 当然 404，但这不等于页面坏了；
2. 当时 `VITE_BASE_URL` 为空或没读到 `.env`（`config.js` 里 `env.VITE_BASE_URL || 默认值`，空串会走默认值，但如果是别的分支/别的 shell 环境变量干扰则可能为空）→ 走相对路径 → 无 proxy → 404；
3. 网关那侧路由/鉴权问题被误记成前端 404。

判断方法很简单：打开 F12 → Network，看请求的 **Request URL** 是 `127.0.0.1:8080` 还是 `localhost:5173`。前者说明代理与此无关；后者才是真命中这个坑。

### 3.4 要不要恢复？

两条自洽的路，**选一条，别混着来**：

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **A. 保持直连（现状，推荐）** | 不恢复 proxy；在 `miniapp/README.md` 补一句「H5 调试必须设 `VITE_BASE_URL`；网关已开 CORS；真机用局域网 IP」 | 与小程序端行为一致（小程序没有代理概念），少一层隐式转发 | 依赖网关 CORS；换机器要改 `.env` |
| **B. 回到同源代理** | 恢复 §3.1 那段；把 `BASE_URL` 默认值改空，让 H5 走相对路径 | 无 CORS 依赖、换 IP 不用改前端、ws 同源 | 必须按平台区分（小程序里相对路径会解析到 `wxfile://`，直接坏），配置复杂度上升 |

如果你只是想要「`curl localhost:5173/api/...` 也能通」的调试便利，那**恢复那段 proxy 是无害的**（因为 `BASE_URL` 仍是绝对地址，恢复后也不会被用到，纯属备用）。但请不要把它记成「修好了一个回归」——它没有修好任何东西。
